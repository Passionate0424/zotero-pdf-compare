# 豆包 × Zotero：开源复用与实现方案

核查日期：2026-11-01。范围：公开项目源码、声明的兼容版本与许可证、独立同步逻辑测试，以及前一阶段的豆包实际下载结果。尚未构建或安装本插件。

## 结论

可开发。豆包网页版的“上传 → 发送 → 预览 → 翻译 → 下载”已经实测成功；Zotero 内的双 PDF 阅读也有可复用源码。根据用户补充要求，**原文在单栏与对照模式中均须保留 Zotero 原生批注功能**。首选架构调整为保留 Zotero 管理的原文阅读器，在旁边增加译文窗格；ZTransplit 主要提供译文窗格和滚动同步的参考实现，再接入我们已验证的豆包浏览器任务。

原文批注是首版必需项，不采用“先交付原文只读双栏、以后再补批注”的验收标准。保留原生宿主阅读器的具体布局方式尚需真实环境原型验证。

这里的可行性不等于已完成端到端插件验证。豆包页面操作的长期稳定性、Zotero 内部阅读器的版本兼容、同页位置联动，仍需在首版原型中实际验收。

## 用户操作与三种阅读模式

1. 在论文或 PDF 附件上右键选择“使用豆包翻译”。首次使用打开独立浏览器，由用户登录；后续复用这个专用登录状态。
2. 插件显示翻译与下载进度。确认 PDF 已完整下载并通过检查后，导入同一文献条目，标题例如“[豆包译文] 原文标题”。独立 PDF 没有父条目时保存为关联的独立附件。
3. 阅读工具栏提供“原文 / 译文 / 对照”，对照时提供“联动滚动”开关，默认打开。

| 模式 | 实现 | 阅读位置 |
| --- | --- | --- |
| 原文 | Zotero 原生原文阅读器 | 保留原文阅读位置与原生批注能力 |
| 译文 | Zotero 原生译文阅读器 | 恢复译文位置；首次进入尽量对应当前原文页 |
| 对照 | 优先保留 Zotero 管理的原文阅读器，在旁边增加译文阅读窗格 | 进入时按当前页与页内位置对齐，双向联动；返回单栏时保留位置和原生批注 |

三种模式由插件统一管理，避免每次切换都打开新的重复标签页。对照模式中原文可批注是首版硬性要求，不能把上游只读配置作为可接受的交付结果。

## 原文原生批注：必需设计与验收

用户已明确要求原文支持 Zotero 原生批注，按原文单栏与对照模式均需支持处理。

首选方案是保持原文的 Zotero 宿主 ReaderInstance、附件身份、事件和批注保存链路，在布局旁增加独立译文窗格。尽量不销毁并重建原文宿主、不替换其批注回调。切换模式、关闭窗格和禁用插件时，均应正确完成未保存操作并恢复原生布局。具体容器嵌入与生命周期仍属原型待验证项，不能仅凭源码分析承诺完整兼容。

这是保留完整原生行为的架构选择：[Zotero 自身的 reader.js](https://github.com/zotero/zotero/blob/main/chrome/content/zotero/xpcom/reader.js) 除了加载、保存与删除批注，还负责只读权限、缓存图像、通知、添加到笔记、标签、复制与拖拽等。仅设置 `readOnly: false` 不足以接上这些功能。

补充核查 [Split View Reader 的实现](https://github.com/zerolfl/zotero-split-view-reader/blob/600f1bd99d9a52a99683702f6681bf34b83bfec3/src/modules/splitView.ts)：它会关闭原宿主后创建两个内部阅读器，加载已有批注，并调用 `Zotero.Annotations.saveFromJSON` 保存。但核查版本中 `onAddToNote`、`onOpenTagsPopup` 和 `onSetDataTransferAnnotations` 等仍是空操作，保存错误也被捕获后忽略。因此，其批注保存代码可供参考，不能据此宣称已经完整支持原生批注体验。

验收规则：

- 原有批注正常显示；原文可使用当前 Zotero 版本提供的批注工具，创建、编辑、改色、评论、标签与删除均正常。
- 批注属于**原始 PDF 附件**，保留 Zotero 原生批注身份与位置；不另建一份仅供插件使用的批注存储，不把批注压平成图像。
- 在对照模式创建批注后，切回原文、关闭并重新打开、重启 Zotero，批注仍可见和编辑。
- “添加到笔记”、复制及拖拽批注等原生操作可用，关联能定位回原文。
- 模式切换、缩放、分隔条调整、联动滚动开关及禁用插件不造成批注丢失、重复或错误归属。选择文字或编辑批注时，不因联动反向触发而拉走原文位置。
- 遵守 Zotero 原有编辑权限；只读库或只读批注不能被插件强行解锁。批注同步沿用 Zotero 配置，并在有同步条件时验证。
- 原译文是不同附件，原文批注不自动复制到译文，避免把不同版面的坐标当成同一份批注。

如果当前版本无法稳定保留原生宿主，必须重新评估布局或完整宿主集成方式；在上述验收通过前，不把对照阅读标为完成，也不以只读原文替代该要求。

## 联动滚动：需要做的优化

现有同步引擎主要同步 `scrollTop / 可滚动总高度`，能够连续滚动，也支持从任意一侧操作。它不是简单的“只同步翻页”。但全篇比例一致不保证同页同位置，尤其在分栏宽度、缩放或页面尺寸不同时。

建议默认使用“**页号 + 页内位置**”：例如左侧视口中心位于第 7 页的 40%，右侧也定位到第 7 页的 40%。两边都读取实时页面边界，计算目标滚动位置并立即写入滚动容器；不要把即时页号和滞后的阅读状态混合，也不使用平滑动画反复追赶。

实现约束：

- 鼠标滚轮、拖动滚动条和键盘导航都能触发；两侧均可作为当前操作侧。
- 每帧最多执行一次同步，目标侧产生的滚动事件不反向触发。
- 缩放或拖动分隔条后暂停映射，待页面重新布局后恢复当前页内锚点。
- 页间空白、首页和末页需要处理边界，避免跳页与振荡。
- 原译文页数或页面对应关系不同，进入显式的页码映射设置；全篇比例同步只能作为标明“近似”的回退。
- 对应页、对应高度只意味着版面位置对齐，不代表句子与段落必然一一对应。

前面测试的豆包文件为 19 页，逐页尺寸与原文一致，适合先做这种同步。这个性质仍需对每次新下载的译文检查。

## 豆包调度与自动下载

推荐结构：`Zotero 插件 → 本机任务服务 → 专用 Chrome + Playwright → 完整 PDF → Zotero 附件导入`。Zotero 的扩展环境不是 Node，不能假定仅在 XPI 里加入 Playwright 就能运行；需要配套本机辅助程序，后续可以由安装器统一配置。

豆包部分采用已实测的页面流程，不依赖尚未验证的官方等价 API，也不假设一定存在可直接请求的永久译文 PDF 地址。

任务应记录排队、等待登录、上传、发送、预览、翻译/导出、下载、校验、导入、完成、失败与取消。翻译和导出可能交叠，不强行用一个固定等待时长推断完成；以页面状态和真正的浏览器下载事件为准。

首版必须补齐：

- 浏览器任务串行执行，避免多个任务同时操作一个预览页；重复点击不创建重复任务或附件。
- 记录来源库、源附件 key、源文件指纹、目标语言、会话地址和结果附件 key，可靠恢复、识别与配对。
- 登录失效时停在“等待登录”，登录后继续；下载超时后先检查已知任务状态，避免盲目重复上传。
- 下载先写入任务临时目录，检查 PDF 可解析、页数及文件完成状态，再导入 Zotero 存储；下载失败或取消不导入残缺附件。
- 插件导入后再记录完成状态；中断恢复时通过持久关联识别已导入结果。
- 本机服务只监听回环地址，以令牌鉴别插件请求，仅处理登记任务的文件路径。

译文作为 Zotero 存储附件后，可以走用户已正确配置的文件同步；插件不会自动完成坚果云等服务的配置。

## 本次实际验证与未验证项

直接导入未修改的上游 `splitViewSync.ts`，使用模拟的两侧阅读器和计时器，执行了以下 6 个独立测试，**6/6 通过**：

1. 左侧滚动驱动右侧。
2. 右侧滚动驱动左侧。
3. 同步写入不会即时回传造成循环，防回环状态按时释放。
4. 一次事件突发只合并为一帧同步。
5. 暂停或关闭期间不继续写入滚动位置。
6. 命名缩放模式可镜像，布局等待后重新采样基线。

这只验证了上游同步引擎的这些逻辑分支；没有运行上游完整测试套件，也没有验证真实 Gecko 事件、双阅读器加载、批注集成或本方案建议的页内映射算法。

豆包端已有一次真实成功导出。结果仍有已知限制：该样本译文为无文字层的图片型 PDF，且第 3 页部分公式截断。阅读模式与同步插件可以解决阅读衔接，不能修复豆包生成的内容缺失。详见同目录的《豆包PDF翻译脚本探查记录》。

## 推荐落地顺序与验收

| 阶段 | 可交付结果 | 必须通过的检查 |
| --- | --- | --- |
| 1：先验证阅读器 | 给定现有原文和已下载译文，在测试环境打开保留原文原生批注的三模式原型 | 原文批注完整验收；两侧连续滚动、跨页、跳页、缩放、调宽、反复切换模式；页内锚点准确，关闭后无持续同步 |
| 2：接完整链路 | 右键触发豆包，自动下载并关联为附件 | 正确处理真实下载事件、登录失效、分钟级等待、失败与取消；重复点击不会重复归档 |
| 3：形成安装版 | 插件 XPI 与本机辅助程序配套安装，日志与恢复入口 | 重启恢复、非英文路径、多 PDF 条目、附件删除、页数不匹配；明确支持的 Zotero 版本 |

第一阶段应直接使用已经下载成功的 19 页样本，先验收 Zotero 阅读体验，避免每轮阅读器调试都重新翻译。完成后接入豆包任务；两部分通过端到端验证后，才能称为可日常使用的插件。
